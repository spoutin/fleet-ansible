# Fleet OS Updates (`fleet-ansible update-os`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a unified `update-os` command and Ansible playbook to `fleet-ansible` that safely applies routine OS package and security updates across Debian, Ubuntu, Alpine, and Red Hat systems with interactive reboot prompts, automated flags, and hypervisor exclusion safeguards.

**Architecture:** A modular Ansible role `roles/system_update` will inspect the OS family and execute distribution-native package managers (APT, APK, DNF) before checking for pending reboots. A top-level playbook `playbooks/update-os.yml` targets `managed_hosts:all:!hypervisors` by default. The `bin/fleet-ansible` bash wrapper provides the `update-os` entry point, parses `--reboot` / `--no-reboot` flags into `reboot_mode`, and passes execution to Ansible with autocompletion and CLI tests.

**Tech Stack:** Bash, Ansible (playbooks/roles, modules: `apt`, `apk`, `dnf`, `package`, `reboot`, `pause`, `stat`), Python 3.

**Spec:** Fleet Operating System Routine Updates (`fleet-ansible update-os`)

## Global Constraints
- Target fleet default: `managed_hosts:all:!hypervisors` (hypervisors are never updated unless explicitly targeted).
- CLI command name: `update-os`.
- Reboot modes: `prompt` (default), `always` (`--reboot`), `never` (`--no-reboot`).
- Distribution support: Debian/Ubuntu (`apt`), Alpine (`apk`), Red Hat derivatives (`dnf`/`yum`).
- Deferred items must be recorded in `TODO.md`.

## Review Focus
1. When running across mixed OS families, the playbook must not fail if an OS lacks a specific reboot detection tool (e.g. `needs-restarting` missing on non-RedHat or lightweight RedHat containers).
2. When running non-interactively without `--reboot` or `--no-reboot`, interactive `pause` prompts should handle terminal disconnects or abort cleanly rather than hanging indefinitely.
3. If `--reboot` is passed, the host must ONLY reboot if an update actually flagged a reboot as required, avoiding unnecessary restarts.
4. When targeting a hypervisor explicitly (e.g., `fleet-ansible update-os pve1`), `ansible_host` resolution from `static_hosts.yml` must succeed as it does for other commands.
5. In Debian/Ubuntu, `autoremove` and cache cleaning must run cleanly after `upgrade`.
